# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

A Telegram bot + mini-website that scrapes and publishes the daily cinema listings for eight Bologna theater circuits (Cineteca, Pop Up Cinema, Circuito Cinema, Nosadella, UCI Meridiana, Cinema Chaplin, Cinema Teatro Galliera, The Space). Runs 24/7 on Oracle Cloud via PM2. Comments/docstrings in the codebase are in Italian; match that style when editing existing files.

## Commands

Standard targets live in the `Makefile`. `make lock` also regenerates `requirements.txt` (see below), and `make broadcast` does a real Telegram send.

Single test: `uv run pytest tests/test_formatter.py::test_name -v`

Multi-day scrape (used to backfill/warm cache for a week): `uv run python main.py --scrape --days 7`.

CI (`.github/workflows/ci.yml`) runs three independent jobs on every push/PR to `main`/`master` via
`astral-sh/setup-uv`: `ruff check` + `ruff format --check`, `mypy .`, and `pytest tests/ -v`. Dependencies and
their exact versions are declared in `pyproject.toml`/`uv.lock` (the source of truth); `ruff`/`mypy` config
lives in `pyproject.toml` (`[tool.ruff]`, `[tool.mypy]`) instead of CLI flags. `requirements.txt` is a
generated export (`make lock`), kept only because the Oracle Cloud deploy (PM2, see Project note above)
installs into `./.venv` with plain `pip install -r requirements.txt` and doesn't have `uv` — don't edit it by
hand, regenerate it with `make lock` whenever a dependency changes.

`.env` (from `.env.example`) is required — `config/settings.py` raises `RuntimeError` at import time if `TELEGRAM_BOT_TOKEN` or `TELEGRAM_CHAT_ID` is missing. Tests avoid this via `tests/conftest.py`, which sets fake env vars with `os.environ.setdefault` before any app import.

## Architecture

Data flows one way: **scrapers → pipeline (+ TMDb enrichment) → SQLite cache → bot/web read from cache only.** Nothing downstream ever hits a scraper source directly; `database/cache.py`'s module docstring states this explicitly.

Packages are split by who depends on what, not by "everything under the bot": `core/` is infrastructure shared
by both consumers (scraping orchestration, scheduling, timeslot definitions), `web/` is the HTTP layer (API +
mini-site), `bot/` is only the Telegram bot itself — it depends on `core/` and `web/` (to start the HTTP
server), but nothing in `core/` or `web/` depends back on `bot/`. `bot/` stayed named `bot` rather than
`telegram/` because `python-telegram-bot`'s importable name is `telegram` — a local `telegram/` package would
shadow the real library on `sys.path`.

- `scrapers/base.py` — `Screening` dataclass (the standardized model every scraper must emit) and `BaseScraper`. `BaseScraper.run()` executes `_fetch()` (and `run_all_dates()` executes `fetch_all_dates()`) via `_call_with_timeout`, a hard timeout (`settings.scraper_timeout` per day, `settings.scraper_total_timeout` for multi-day) that really returns control: it calls `shutdown(wait=False)` instead of using `with ThreadPoolExecutor(...)`, whose exit would wait for the scraper anyway. Both catch all exceptions, always returning a result with `success=False, error=...` instead of raising — one broken cinema site can never crash the pipeline. Both also stamp `Screening.circuito` with the scraper's `slug` (`Screening.cinema` is the room, not the circuit). Concrete scrapers only implement `_fetch(target_date) -> list[Screening]`; multi-day scraping optionally overrides `fetch_all_dates()` to do one HTTP request instead of N (avoids 429s).
- `scrapers/_tickets18.py` — shared HTML parser for the "18tickets" ticketing platform, reused by Cineteca, Pop Up, Circuito Cinema, and Nosadella. `parse_all_dates()` is the single extraction path, grouping every showing by date; `parse_day()` is just `parse_all_dates(..., max_days=1)` filtered to one date. Showtimes are matched via `data-time` (ms epoch UTC) converted to `Europe/Rome`; there's a regex-based text fallback for pages without `data-time`.
- `scrapers/_tickets18_base.py` — two `BaseScraper` subclasses built on top of `_tickets18.py` so concrete scrapers stay declarative: `SingleTheaterScraper` (one 18tickets page lists every room — Nosadella, Pop Up) and `MultiTheaterScraper` (one 18tickets page per room, fetched in parallel and merged — Cineteca, Circuito Cinema). Subclasses just set `base_url`/`theaters` + `label` (the string appended to each `Screening.note`); `MultiTheaterScraper._fetch_html()` and `SingleTheaterScraper._post_process()` are the two override points (used by Circuito Cinema for HTTP retry-on-429, and Pop Up for promoting the room name into `Screening.cinema`).
- `scrapers/uci.py` — talks to UCI's own API directly instead of scraping HTML.
- `scrapers/chaplin.py`, `scrapers/galliera.py` — WordPress sites with no ticketing platform: the schedule is hand-written free text (Chaplin: one "Orari e giorni programmazione" block per film page; Galliera: a single "Agenda spettacoli" post found via the `cinema` category). Both parse Italian dates/times with `scrapers/_dates_it.py` (year inferred from today) and fetch once for all days.
- `scrapers/thespace.py` — The Space Bologna (cinema id 1003) via its JSON API `/api/microservice/showings/cinemas/{id}/films`; the API answers 401 until the page visit sets an anonymous token cookie, so the scraper GETs the cinema page first (same `requests` session) and then the API. One call returns every film with all upcoming days.
- `scrapers/tmdb.py` — `TmdbClient`, optional (`tmdb.enabled` is false without `TMDB_API_KEY`); enriches `Screening` objects in place with rating, genre, high-res poster, overview, runtime, using a local SQLite cache (`data/tmdb_ratings.sqlite3`) with a 7-day TTL to avoid hitting the TMDb API repeatedly for the same title.
- `scrapers/__init__.py` — `ALL_SCRAPERS` is the registry list; adding a new cinema circuit means creating a new `BaseScraper` subclass and appending its class here.
- `core/pipeline.py` — orchestrates one scrape cycle: runs every scraper in `ALL_SCRAPERS` concurrently (`ThreadPoolExecutor`), collects `Screening`s, enriches via `TmdbClient` if enabled, then writes to `Cache`. Two entry points: `run_scrape_pipeline` (single day, or a loop of single-day scrapes) and `run_multi_day_pipeline` (scrapes each circuit exactly once and extracts N days of showtimes from that one response — the "avoid 429" optimization mentioned above). Scraper failures become warning strings surfaced through the cache/API/messages rather than raised exceptions. A circuit that fails, or returns zero screenings (in multi-day: across the whole window — usually broken selectors), keeps its screenings from the previous snapshot of the same day (matched by `Screening.circuito`, past showtimes dropped for today) instead of vanishing until the next successful 15-minute refresh; snapshots are written with `Cache.store_snapshot()`, which unlike `Cache.store()` derives no per-day "no screenings" warnings. Also exposes `today()` (timezone-aware current date), reused by both `bot/` and `web/`.
- `core/scheduler.py` — `CinemaScheduler` wraps `AsyncIOScheduler` (APScheduler) with four jobs, all `Europe/Rome`, `max_instances=1`, `coalesce=True`: daily scrape (`SCRAPE_CRON_HOUR/MINUTE`), daily broadcast (`BROADCAST_CRON_HOUR/MINUTE`), a periodic refresh every `REFRESH_INTERVAL_MINUTES` that re-runs the scrape job, and a nightly backup (`BACKUP_CRON_HOUR`). Broadcast always reads from the cache the scrape job just populated — they never race on scraping the same data. Instantiated and started inside `CinemaBot` (the app's single blocking entry point), even though what it schedules is shared infrastructure, not Telegram-specific.
- `core/alerts.py` — `CircuitHealth` (module singleton `circuit_health`) counts consecutive failures per circuit, recorded by `run_multi_day_pipeline` only (in the single-day path zero screenings on one day can be legitimate). It queues one `Alert` when a circuit reaches `ALERT_AFTER_FAILURES` and one when it recovers; `CinemaBot._send_alerts()` drains the queue after each scrape job and sends to `ADMIN_CHAT_ID` (never the broadcast chat), so `core/` never imports `bot/`.
- `core/backup.py` — `backup_cache()` copies the cache with SQLite's backup API (`Cache.backup()`, consistent even mid-write) to `BACKUP_DIR/cache-YYYY-MM-DD.sqlite3`, keeping the newest `BACKUP_KEEP`.
- `core/timeslots.py` — `TIMESLOTS` (four fixed time-of-day slots: Mattina/Pomeriggio/Sera/Notte) and `parse_time()`, used by `bot/formatter.py`'s timeslot-mode Telegram digest. Lives in `core/` (not `bot/`) because it's meant to be a shared definition, not Telegram-specific.
- `database/cache.py` — `Cache` wraps a SQLite `snapshots` table keyed by ISO date, storing screenings + warnings as a JSON payload, plus broadcast-dedup bookkeeping (`is_broadcast_done_today` / `mark_broadcast_done`) so the daily broadcast job doesn't double-send on restart. `_SCREENING_FIELDS` filters stored JSON keys against the current `Screening` dataclass fields on load, for backward compatibility with older cached payloads.
- `bot/telegram_bot.py` — `CinemaBot`, the `python-telegram-bot` app: wires up the scheduler's callbacks, the `/cinema` command handler, and lifecycle (`run()` is the blocking entry point used by `main.py` with no flags — it also starts `core.scheduler` and `web.server.start_api_server()`, making this the single process that runs everything).
- `bot/formatter.py` — renders `CacheSnapshot` into Telegram HTML messages, chunked to fit message-size limits (`render_snapshot` returns an iterable of message chunks); automatically appends an "Avvisi" (warnings) section listing circuits that failed to scrape.
- `web/server.py` — assembles the FastAPI `app` (CORS, static mount at `/static` from `web/static/`) and includes the two routers below. `app.include_router(api.router)` runs before `app.include_router(site.router)` — `/health` is a single path segment, same shape as `site.py`'s catch-all `/{date_param}`, so the order determines which one a request to `/health` actually hits.
- `web/api.py` — JSON REST: `/health`, `/api/screenings`, `/api/cinemas`, `/api/history`, `/api/stats`, `/api/refresh`. Swagger UI at `/docs`. `POST /api/refresh` requires the `X-Refresh-Token` header matching `REFRESH_TOKEN` (endpoint returns 404 when unset) because each call hits every cinema site; CORS allows only `GET`.
- `web/site.py` — the mini-site: `/`, `/{YYYY-MM-DD}`, `/partials/{date}` (HTML fragment consumed by the page's own JS on day-switch), `/robots.txt`, `/sitemap.xml`, rendered via Jinja2 templates in `web/templates/`. Owns the business logic for grouping raw `Screening`s into deduplicated films (`_build_film_list`) and the SEO head (`_seo_context`): per-day title/description, canonical (today is `/`, other days `/{date}`), `noindex, follow` on past days or days without data, and a JSON-LD `@graph` with one `ScreeningEvent` per showtime referencing `Movie`/`MovieTheater` nodes by `@id`. Every absolute URL goes through `web_utils.absolute_url()`, which prefers `PUBLIC_BASE_URL` — behind nginx `request.url` is `http://127.0.0.1:8080`. Page routes use `api_route(..., methods=["GET", "HEAD"])`: FastAPI's `@router.get` answers 405 to HEAD, which uptime monitors use. The partial also carries `title` and `day-label` slots so the JS day-switch updates `document.title` and the hidden part of the `<h1>`.
- `web/web_utils.py` — `get_cache()` (the shared `Cache` singleton), `parse_date()`, and `in_window()` (site pages and partials 404 outside today −90/+14 days, so crawlers can't generate unbounded URLs), used by both `api.py` and `site.py` by importing the module (`from web import web_utils`) rather than the function directly, so a single `patch("web.web_utils.get_cache", ...)` in tests covers both routers.
- `config/settings.py` — single frozen `Settings` dataclass loaded once at import time from `.env` (via `python-dotenv`); everything else imports the module-level `settings` singleton rather than reading env vars directly.
- `main.py` — CLI entry point: no flags (`CinemaBot().run()`: bot + scheduler + web server thread in one process, used by Docker), `--bot` / `--web` (the production split, one PM2 app each in `ecosystem.config.js`: bot + scheduler without the web thread, and `web.server.run_api_server()` alone; they share the SQLite cache, which `Cache` opens in WAL mode), `--scrape [--days N]` (pipeline only, prints counts, no Telegram), `--broadcast` (scrape + actually send to the configured chat — used for testing message formatting). In the split setup `/api/refresh` runs the pipeline in the web process, so its circuit alerts aren't sent (the queue is per-process).

## Testing conventions

`tests/conftest.py` defines shared fixtures (`sample_screening`, `sample_screenings`, `target_date`) and several `MOCK_HTML_*` fixtures with hand-written 18tickets-style HTML for exercising `scrapers/_tickets18.py` without network access. When adding a scraper test, prefer extending these mocks over hitting real sites.
